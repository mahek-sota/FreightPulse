The problem

Thousands of trucks, one messy stream

A freight broker tracks thousands of loads at once. Each load sends a stream of events: tendered to a carrier, accepted, arrived at the pickup dock, departed, a GPS ping every minute or two from the truck's electronic logging device (ELD), arrived at delivery, delivered.

Those feeds are unreliable. Events arrive late, twice, out of order, or corrupted. Yet operations needs answers in seconds: Where is the truck? Will it make its delivery appointment? Is the driver stuck at a dock, running up detention charges at $75 an hour? Analytics needs the same data modelled properly to score lanes and carriers.

FreightPulse covers the whole path: ingestion, stream processing, relational storage, and an API.

What it answers

  • Shipment state: CREATED through DELIVERED, never moving backwards even when events arrive out of order.
  • ETA: distance by road to the next stop, a smoothed truck speed, plus the 10-hour rest a driver must take after 11 hours of driving.
  • Late-risk alerts: MEDIUM within 30 minutes of the appointment window closing, HIGH once past it. Raised only when the level changes.
  • Detention alerts: a truck at a dock for more than 2 hours, escalating at 3 and 4 hours, with the cost estimated.
  • Stale-tracking alerts: a truck in transit with no GPS for more than an hour.
  • Lane and carrier analytics: on-time %, transit time, acceptance rate, tracking compliance.

System design

Architecture

Every event is keyed by shipment_id, so all of a shipment's events stay in order on one Kafka partition. The two input topics have the same partition count and the processor group uses the range assignor, so a shipment's lifecycle events and its GPS pings are handled by the same processor instance.

What happens to one batch

The core guarantee is at-least-once delivery plus idempotent writes, which together give effectively-once results. Kafka offsets are committed only after the database transaction commits. A crash at any point either replays the batch (and duplicates are skipped by event_id) or loses nothing.

  1. Consume up to 1,000 messages from both topics. Auto-commit is off, so nothing is acknowledged yet.

  2. Validate every message against its schema. Bad ones are set aside for the DLQ.

  3. Prepare: make sure the day's partitions exist and upsert any new lanes, each in its own short transaction.

One database transaction

  1. Insert new shipments and their stops.

  2. Skip any event_id already in the log (redeliveries, producer retries).

  3. Fold each remaining event through the pure reducer: status, stops, position, ETA, late risk.

  4. Append events with ON CONFLICT DO NOTHING, then UPDATE … WHERE version = expected.

  5. Publish alerts and DLQ records and flush them, then COMMIT.

  1. Commit Kafka offsets, synchronously, only after the database commit.

Crash before the commit: the batch is replayed and nothing was written. Crash after it: the batch is replayed and every event is skipped as already logged.

How it works

The rules inside the processor

Shipment state machine

Statuses have a rank along the main path. A forward jump is always allowed (a truck's geofence events are sometimes missed). A move backwards with a newer timestamp is invalid and goes to the DLQ. EXCEPTION sits on top of the current status and returns to it when resolved.

Out-of-order events

The log always records every valid event. Only the derived state follows ordering rules, and each part of it has its own event-time check:

Part of stateChanges only if
Statusthe event is newer than the event that set the current status
Position, speed, ETAthe ping is newer than the last ping
Stop arrival / departurealways: earliest arrival and latest departure win
Carrier, ratethe tender event is the newest of its kind

Hypothesis checks two properties: any shuffle of a valid lifecycle ends in the same state as the ordered one, and no random event sequence ever moves the status backwards.

ETA

miles = haversine × 1.18
speed = EWMA of pings ≥ 5 mph
drive_h = miles / speed
breaks = ⌈(drive_h − hos_left) / 11⌉
eta = now + drive_h + 10 h × breaks

1.18 is the road circuity factor. Confidence falls when pings are stale or speed varies a lot.

Bad data → DLQ

  • SCHEMA_VALIDATION: corrupt JSON or fields
  • UNKNOWN_SHIPMENT: still no shipment.created after 30 s parked
  • INVALID_TRANSITION: e.g. departed after delivered
  • IMPOSSIBLE_GPS_JUMP: implied speed over 100 mph
  • UNKNOWN_REFERENCE: unknown carrier or facility

make dlq-replay re-sends them after a fix.

Why the scanners use event time, not the wall clock

The simulator runs 60× faster than real time, and replayed history must raise alerts on the history's own timeline. So the detention and stale-tracking scanners use a fleet clock: the newest event time any processor has committed, stored per partition in stream_watermarks.

Found by measuring

Bugs the benchmarks and demo caught

Processors deadlocked each other

The first benchmark showed 3 processors no faster than 1 (1.05×). A CPU sample read 0% + 0% + 68%: two had crashed with DeadlockDetected, inserting the same new lanes in opposite order. Lanes are now upserted in sorted order in a short transaction of their own, and deadlocks are retried. Result: 2.15× scaling, and a regression test with 3 live processors.

One bad first GPS fix poisoned a track

A corrupt first ping can't be checked against anything, so it became the anchor and every good ping after it was rejected: 15 good pings dead-lettered for one truck. Now, if two rejected pings agree with each other, the anchor was the outlier and the track re-anchors.

Keyset pagination wasn't fast

8.7 ms instead of under 1 ms. Postgres carries an equality across a join but not a range, so the cursor applied to one table only and the other was scanned from row 1. Repeating the bound on both tables: 0.098 ms.

Out-of-order lifecycle events froze the ETA

Stop events often reach the processor after newer pings from the other topic, so they counted as "older" and never refreshed the ETA. Now a stop or status change recomputes the ETA as of the latest known position.

Testing

139 tests, 90% coverage where it matters

Unit & property

ETA, HOS and haversine math; the state machine under Hypothesis; simulator determinism and chaos rates; alert rules; no I/O imports in the domain layer.

Integration

Real Redpanda and Postgres containers. Duplicates produce exactly one row; shuffled order gives the same state; bad events land in the DLQ; parking and expiry; DLQ replay; scanners; rollups; 3 concurrent processors.

Crash tests

The processor runs as a subprocess and is killed before the DB commit, after it, and at a random moment with SIGKILL. After a restart, the row counts are exact: nothing lost, nothing duplicated.

What I'd do next

  • Avro or Protobuf with a schema registry, for compact payloads and enforced compatibility.
  • Flink or Kafka Streams for per-shipment state, windows and watermarks, with exactly-once sinks.
  • CDC with Debezium from the TMS database, instead of the TMS publishing events itself.
  • An Iceberg lakehouse sink for cheap long retention and ML features for ETA models.
  • Multi-region Kafka with replication and read replicas for the API.
  • Process partitions in parallel inside one instance, the main limit measured above.
