## 1. Shipment timeline: composite index `(shipment_id, event_time)` vs sequential scan

**Query purpose:** `GET /shipments/{id}/timeline`: every lifecycle event of one shipment, ordered.

**Change:** `CREATE INDEX ix_events_shipment_time ON shipment_events (shipment_id, event_time)`

```sql
SELECT event_id, event_type, event_time, payload FROM shipment_events WHERE shipment_id = 'SHP-0123457' ORDER BY event_time
```

| Variant | Median exec | Planning | Scan nodes | Relations scanned |
|---|---:|---:|---|---:|
| before: no index (seq scan of every partition) | 31.874 ms | 0.218 ms | Parallel Seq Scan x32, Seq Scan x8 | 40 |
| after: composite index | 0.201 ms | 0.226 ms | Index Scan x32, Seq Scan x8 | 40 |

| Index | Size (all partitions) |
|---|---:|
| `ix_events_shipment_time` | 39.2 MB |

The timeline filters on `shipment_id` but the table is partitioned on `event_time`, so there is no pruning: without an index Postgres reads every daily partition in full. The composite index turns each partition into a short index range scan that already returns rows in `event_time` order, so no sort is needed. The remaining cost is one index probe per partition, which is why retention (ADR 0004) keeps the partition count bounded.

## 2. GPS time-range scan: partition pruning, B-tree vs BRIN on `event_time`

**Query purpose:** Fleet-wide analytics over a 2-hour window of pings (rollups, heat maps).

**Change:** Partition pruning (daily partitions) plus `CREATE INDEX ix_pings_time_brin ON gps_pings USING brin (event_time) WITH (pages_per_range = 32)`, compared with a B-tree on the same column

```sql
SELECT count(*), round(avg(speed_mph)::numeric, 1) FROM gps_pings WHERE event_time >= '2026-10-27T07:00:00+00:00' AND event_time < '2026-10-27T07:00:00+00:00'::timestamptz + interval '2 hours'
```

| Variant | Median exec | Planning | Scan nodes | Relations scanned |
|---|---:|---:|---|---:|
| before: pruning off, no event_time-leading index (planner full-scans the PK) | 37.562 ms | 0.313 ms | Index Scan x30, Seq Scan x10 | 40 |
| pruning only (1 partition, seq scan) | 4.603 ms | 0.126 ms | Seq Scan x1 | 1 |
| pruning + B-tree on event_time | 1.637 ms | 0.355 ms | Index Scan x1 | 1 |
| after: pruning + BRIN on event_time | 1.675 ms | 0.148 ms | Bitmap Heap Scan x1, Bitmap Index Scan x1 | 1 |

| Index | Size (all partitions) |
|---|---:|
| `ix_pings_time_brin` | 960.0 kB |
| `ix_pings_time_btree` | 107.9 MB |

(For a clean baseline the composite `(shipment_id, event_time)` index is dropped during this case; otherwise the planner full-scans it, filtering on its second column.) Partition pruning does most of the work: a 2-hour predicate on `event_time` touches one daily partition instead of all of them. Inside that partition a time index avoids reading the other ~22 hours. Because pings are appended in time order, BRIN's per-block-range min/max summaries are tight, so BRIN skips almost as well as a B-tree while being a tiny fraction of its size (see the size table). That is why the migration ships BRIN and not a B-tree on `event_time` for this append-only table.

## 3. Shipment list: keyset pagination vs `OFFSET 100000`

**Query purpose:** `GET /shipments` deep in the result set (page 2,001 of 50).

**Change:** `WHERE c.shipment_id > :cursor ORDER BY c.shipment_id LIMIT 50` instead of `OFFSET`

```sql
SELECT c.shipment_id, c.status, s.customer_id, s.carrier_id, s.lane_id, l.origin_facility_id, l.dest_facility_id, c.late_risk, c.eta, c.miles_remaining, c.last_ping_at, c.updated_at FROM shipment_current_state c JOIN shipments s ON s.shipment_id = c.shipment_id JOIN lanes l ON l.lane_id = s.lane_id ORDER BY c.shipment_id OFFSET 100000 LIMIT 50;
-- vs
SELECT c.shipment_id, c.status, s.customer_id, s.carrier_id, s.lane_id, l.origin_facility_id, l.dest_facility_id, c.late_risk, c.eta, c.miles_remaining, c.last_ping_at, c.updated_at FROM shipment_current_state c JOIN shipments s ON s.shipment_id = c.shipment_id JOIN lanes l ON l.lane_id = s.lane_id WHERE c.shipment_id > 'SHP-0100001' AND s.shipment_id > 'SHP-0100001' ORDER BY c.shipment_id LIMIT 50
```

| Variant | Median exec | Planning | Scan nodes | Relations scanned |
|---|---:|---:|---|---:|
| before: OFFSET 100000 LIMIT 50 | 48.297 ms | 0.179 ms | Index Scan x3 | 3 |
| keyset, cursor on one join input only | 9.634 ms | 0.222 ms | Index Scan x3 | 3 |
| after: keyset, cursor on both join inputs (what the API runs) | 0.098 ms | 0.178 ms | Index Scan x3 | 3 |

`OFFSET n` still has to produce and discard the first n joined rows, so its cost grows linearly with the page number. A keyset cursor seeks directly to the last seen `shipment_id` through the primary-key index and reads only the 50 rows it returns, so every page costs the same. Keyset pages are also stable while rows are being inserted, which matters for a live fleet. One subtlety showed up in the measurements: with the cursor only on `shipment_current_state`, the merge join still read `shipments` from its first row, because Postgres propagates equality across join keys but not range predicates. Repeating the bound on the other join input (`AND s.shipment_id > :cursor`) lets both index scans start at the cursor; the API query does exactly that.

## 4. Carrier scorecard: raw aggregation over events vs the rollup table

**Query purpose:** `GET /carriers/{id}/scorecard?days=30`.

**Change:** Read `carrier_scorecard_daily` (maintained by the jobs service) instead of aggregating raw events

```sql
SELECT day, tenders, acceptance_rate, on_time_delivery_pct FROM carrier_scorecard_daily WHERE carrier_id = 'CAR-007' AND day >= (now() - interval '30 days')::date ORDER BY day
```

| Variant | Median exec | Planning | Scan nodes | Relations scanned |
|---|---:|---:|---|---:|
| before: aggregate shipment_events + stops on every request | 68.417 ms | 0.701 ms | Bitmap Index Scan x1, Index Scan x1, Parallel Bitmap Heap Scan x1, Parallel Seq Scan x32, Seq Scan x7 | 41 |
| after: read carrier_scorecard_daily | 0.017 ms | 0.016 ms | Index Scan x1 | 1 |

ON CONFLICT DO UPDATE`, so the API reads about 30 pre-aggregated rows by primary key. The trade-off is freshness: the scorecard lags by up to one rollup interval (60-120 s), which is fine for a daily metric.

## 5. (Bonus) Partial index on active alerts

**Query purpose:** Active alerts for a shipment (detail page badge, scanners' resolve checks).

**Change:** `CREATE INDEX ix_alerts_active_shipment ON alerts (shipment_id) WHERE resolved_at IS NULL`

```sql
SELECT * FROM alerts WHERE shipment_id = 'SHP-0022614' AND resolved_at IS NULL
```
