# Benchmarks

> Generated by `make bench` (`src/freightpulse/perf/bench.py`) on 2026-11-10 22:19 UTC. Every number below was measured in that run. Raw data: `docs/benchmarks_results.json`.

## Machine

- Host: Apple M5 Pro, 15 cores, 24 GiB RAM; Darwin 25.5.0 (arm64); Python 3.12.14.
- Docker VM (Redpanda + Postgres): 4 CPUs, 4124446720 bytes.
- Processors run as host subprocesses (one Python process each), talking to Redpanda and Postgres in Docker over localhost. Everything shares one laptop, so treat the numbers as a lower bound for dedicated hardware.

## Workload

Simulator events with the default chaos mix (2% duplicates, 3% out-of-order, 0.5% malformed, 1% GPS dropout); about 95% GPS pings and 5% lifecycle events. Processor batch size 1000, one Postgres transaction per batch, offsets committed after the DB commit. Before every measurement the harness waits until the consumer group is Stable with all N members owning partitions, so no rebalance falls inside a measured window.

## Reading the numbers

- **The batching window sets the latency floor.** The processor calls `consume()` for up to 1,000 messages or 0.25 s, whichever comes first, then commits one transaction. At low rates a batch waits for the timeout; at higher rates it fills sooner. So latency doesn't rise steadily with load until the group nears saturation. Smaller batches or a shorter timeout trade throughput for latency.
- When committed ev/s keeps up with offered ev/s and p99 stays flat, the group is below saturation. Above the capacity measured in A, a backlog builds and latency climbs with it.
- **Per-instance ceiling.** A processor handles one batch at a time: consume, one Postgres transaction, then a synchronous offset commit. If its CPU (snapshot above) is well below 100% while throughput plateaus, the instance is bound by those serial round trips rather than by CPU, and more instances overlap the waits.
- **Group scaling.** Three instances get two partitions of each topic (range assignor). They all write to one Postgres in the same 4-CPU Docker VM as Redpanda, so the snapshot's Postgres CPU is the resource to watch as instances are added.
